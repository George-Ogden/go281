!markdown # Tooling I've been writing my own development tools recently. It started when I wanted a simpler way to debug programs, so I made a library for it. I kept forgetting to delete my debugging code, so I made a tool to check that I deleted it. I observed other frequent mistakes, so I added checks for those as well. All these tools led to duplication between my repositories, so I wrote a way to manage that efficiently. Now, my other projects rely on these tools, and I'm sure there'll be more soon. There's an immensely satisfying feeling when it works in the wild. I feel overjoyed with excitement that the time I invested to make it is paying off at that moment. Usually, this means I get an error message before I make a common mistake. And then there's one less thing I have to think about when working, because the tool handles it. As with all projects, this provided me with an opportunity to refine my processes. One limitation they highlighted is how when I focused only on the next feature, I often had to do heavy refactoring when more were added. However, when I considered future versions, I could make future-proof architectural decisions. Using these tools also gave me a chance to experiment with design by dogfooding. I could get feedback as I used the tools and concentrated more on the often-neglected features, such as clear error messages and internal logging. The joy of success is sweetened by the unanticipated frustration that I encounter. This is not unique to tooling, but when I am forced to interact with existing libraries and tools, rather than write from scratch, it becomes a more obstructive problem. For example, I wanted to make some modifications to a library I used, so I submitted a GitHub pull request. Before it was approved, there was some back-and-forth between changes, which relied on another human somewhere across the world to review and accept my contribution before I became fully unblocked. It felt like I was being diverted by an unimportant problem that should not have existed, but required substantial effort to resolve. Making the tools often required unfamiliar steps, such as packaging for easy installation. Again, these felt like unnecessary obstacles when I wanted such a simple outcome. Nevertheless, I invested time up front to learn about the vast options and configurations, which paid off when I used it in later projects. I use many existing tools, but there are sometimes limitations. In many cases, it is possible to find a workaround rather than make my own. However, for these tools, I was neither satisfied with the alternatives nor the workaround. Often, the minimal version seemed simple. However, I could often think of improvements, so it grew into a large, complex project that I had invested an unforeseeably large amount of time and energy into. Perhaps if I had seen all of the challenges before starting, I might have stuck with the limited version. However, my only regrets are that I had previously made so few tools and that those were of poorer quality. As I discover new limitations, I hope to keep developing these tools. At least for me, they make the development process much smoother. Hopefully, they can have a similar effect on others. If not, I have something that frequently makes my life easier and it gave me another opportunity for self-improvement.
